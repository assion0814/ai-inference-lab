# RK3588 具身智能改造方案（摄像头 + 语音唤醒 + 十轴 IMU）

> 日期：2026-10-22 · 硬件：Orange Pi 5 Plus（RK3588 8GB）+ 亚博智能三件套
> 背景：之前 RK3588 只做了 LLM/CNN 推理（纯软件），现在有了**视觉 + 听觉 + 姿态**
> 定位：从「跑分板」变成「能感知的具身智能终端」

**实测证据：**

| 检查项 | 结果 | 说明 |
|---|---|---|
| 网线物理连接 | ✅ `enp2s0 carrier=1` | 链路建立 |
| 协商速率 | ✅ **2.5Gbps/Full** | 板子 PHY 通电并协商成功 |
| 板子 IP 192.168.66.129 | ❌ 不响应 | ping/SSH 都失败 |
| 全 192.168.66.0/24 扫描 | ❌ 无任何主机 | 254 个 IP 全不通 |
| tcpdump 抓包 | ❌ 只有主机自己的广播 | **板子不发任何包** |
| ARP 应答 | ❌ 无 | 连 ARP 层都不响应 |

**⇒ 判断：板子通电了（PHY 工作），但操作系统没有运行起来，或网络没配置。**

**最可能的原因（按概率排序）：**

1. **加硬件导致开机失败**（最可能）
   - MIPI 摄像头排线接反/短路 → 电源保护
   - 语音模块 UART 与调试串口冲突（`ttyS2` 是 console）
   - IMU I2C 地址冲突或上拉缺失
2. **供电不足** —— 三件套 + 板子可能超过 5V/3A
3. **系统卡在启动**（文件系统损坏、内核 panic）

**下一步：** 运行 `hw_probe.sh` 诊断（见 §五）

## 一、硬件解读：亚博智能三件套是什么

### 1.1 摄像头

**亚博智能常见两款：**

| 型号 | 接口 | 分辨率 | 特点 |
|---|---|---|---|
| **USB 摄像头** | USB 2.0/3.0（UVC）| 1080p/4K | 即插即用，延迟 30-60ms |
| **MIPI CSI 摄像头** | 15/22 pin FPC | 1080p | 走 RK3588 ISP，延迟 <20ms |

**RK3588 的 ISP 能力**（这颗芯片的隐藏优势）：
- 支持 **4 路 MIPI CSI 同时输入**
- 硬件 3A（自动曝光/白平衡/对焦）
- 硬件降噪、HDR、鱼眼校正
- **ISP 处理不占 CPU/NPU**

**⇒ 如果买的是 MIPI 摄像头，能用 RK3588 的 ISP 做硬件级图像处理，
这是 RK3588 相对普通 USB 摄像头的真实优势。**

### 1.2 语音唤醒模块

**亚博智能常见三种：**

| 型号 | 接口 | 唤醒方式 | 特点 |
|---|---|---|---|
| **SU-03T** | UART（3.3V TTL）| 离线关键词 | 无需联网，成本低 |
| **ReSpeaker 2-Mic HAT** | I2S + GPIO | 离线 + 可编程 | 双麦阵列，可做声源定位 |
| **USB 麦克风阵列** | USB Audio | 需软件唤醒 | 通用性最好 |

**关键技术点：**
- **SU-03T 类模块**：唤醒后通过 UART 输出一个字节（或拉 GPIO），
  板子收到后启动录音 → 送 ASR → 送 LLM
- **ReSpeaker 类**：I2S 直连 RK3588，可做 **波束成形 + 声源定位**（6 麦）

**⇒ 唤醒模块的价值是「省电 + 隐私」：**
不需要一直跑 ASR，只有唤醒词触发后才启动完整链路。

### 1.3 十轴传感器

**"十轴"的构成**（通常是一个模组或两个芯片）：

| 轴 | 传感器 | 测量 |
|---|---|---|
| 3 | 加速度计 | ±2/4/8/16 g |
| 3 | 陀螺仪 | ±250/500/1000/2000 °/s |
| 3 | 磁力计 | ±4800 µT（地磁）|
| 1 | 气压计 | 300-1100 hPa（高度）|

**常见芯片组合：**
- **MPU9250**（9 轴）+ BMP280（气压）= 10 轴
- **ICM20948**（9 轴）+ BMP280 = 10 轴
- **MPU6050**（6 轴）+ HMC5883（磁）+ BMP280 = 10 轴

**接口**：I2C（0x68/0x69）或 SPI

**⇒ 十轴的价值是「知道自己在哪、朝哪、怎么动」：**
- 姿态解算（roll/pitch/yaw）
- 步数/运动检测
- 高度变化（气压）
- 指南针

## 二、三个模块合起来能做什么

### 2.1 单模块能力

| 模块 | 单独能做 |
|---|---|
| 摄像头 | 目标检测、人脸识别、OCR、VLM 图文问答 |
| 语音唤醒 | 离线唤醒词、语音指令、声源定位（多麦）|
| 十轴 IMU | 姿态解算、运动检测、指南针、高度计 |

### 2.2 ★ 组合能力（真正的价值）

**① 语音触发的视觉问答（最实用）**
```
说"小亚小亚" → 唤醒 → 摄像头拍照 → RK3588 NPU 跑 YOLO/VLM →
LLM 生成回答 → TTS 播报
```
**这就是一个完整的本地语音助手**，全程离线。

**② 姿态感知的视觉稳定**
```
IMU 检测到抖动 → 摄像头图像做电子防抖（EIS）
```
对移动机器人/手持设备有用。

**③ 事件触发式监控**
```
摄像头检测到运动 → IMU 确认不是自身震动 → 拍照 + LLM 描述 + 报警
```
能过滤误报（风吹动摄像头 vs 真实入侵）。

**④ 具身导航（如果装在移动平台上）**
```
IMU 提供航向 → 摄像头识别地标 → LLM 规划路径
```

**⑤ 多模态记录仪**
```
每秒记录：图像 + 姿态 + 位置 → 事后用 LLM 做检索/总结
```

## 三、技术可行性评估（基于已有实测数据）

### 3.1 RK3588 的算力够不够

**已实测的能力（前项目）：**

| 任务 | RK3588 实测 | 需求 | 余量 |
|---|---:|---|---|
| YOLOv8n INT8 @640 | **62 FPS** | 30 FPS 够用 | ✅ 2× |
| YOLOv8s INT8 @640 | 33.7 FPS | 30 FPS | ⚠️ 临界 |
| Qwen2.5-0.5B W8A8 | **32.17 tok/s** | 对话够用 | ✅ |
| Qwen2.5-1.5B W8A8 | 14.57 tok/s | 略慢 | ⚠️ |
| ResNet50V2 @224 | 109.8 FPS | — | ✅ |

**⇒ 组合任务的预算：**
```
语音唤醒（SU-03T 硬件，0 算力）
  → VAD + ASR（需外挂，或云端）
  → YOLO 检测（62 FPS，可实时）
  → LLM 回答（0.5B @ 32 tok/s，一句话 2 秒）
  → TTS（需外挂）
```

**关键缺口：ASR 和 TTS 在 RK3588 上没有现成方案！**
- RKLLM 只有 LLM，没有 ASR/TTS
- 需要额外部署 Whisper（CPU/NPU）或接云端

### 3.2 内存预算

RK3588 只有 8GB，而且：
- NPU 的 DMA 上限只有 2.3GB（前项目实测，3B 模型跑不了）
- 视觉模型 + LLM 同时跑需要仔细分配

**估算：**
```
系统 + 桌面      : 1.5 GB
YOLOv8n INT8     : 0.05 GB
Qwen2.5-0.5B W8A8: 0.6 GB
Whisper tiny     : 0.1 GB
图像缓冲         : 0.5 GB
─────────────────────────
合计             : ~2.8 GB / 7.7 GB   ✅ 充裕
```

### 3.3 延迟预算（端到端语音助手）

```
唤醒检测        :  <100 ms（硬件）
录音 + VAD      :  300 ms（说完一句话）
ASR（Whisper tiny）: 500-800 ms（CPU）
LLM 首 token    :  100 ms
LLM 生成 20 token: 600 ms（0.5B @ 32 tok/s）
TTS             :  300-500 ms
─────────────────────────────
总计            :  ~2.0-2.5 秒
```

**⇒ 能接受，但不算快。优化空间在 ASR（换 NPU 加速）和 TTS。**

## 四、实施路径（分三阶段）

### 阶段 1：硬件点亮（1-2 天）

**目标：三个模块都能读到数据**

```
1. 摄像头
   - USB: v4l2-ctl --list-devices → /dev/video0
   - MIPI: 检查 dmesg 的 rkisp 日志 → /dev/video0..4
   - 验证: ffmpeg -f v4l2 -i /dev/video0 -frames:v 1 test.jpg

2. 语音唤醒
   - SU-03T: 接 UART（注意避让 ttyS2 调试口）→ /dev/ttyS3 或 /dev/ttyS7
   - ReSpeaker: arecord -l 看声卡
   - 验证: cat /dev/ttyS3 | xxd（说唤醒词看有没有字节）

3. IMU
   - i2cdetect -y 1 → 找 0x68/0x69/0x76/0x77
   - 验证: 读 /sys/bus/iio/devices/iio:device*/in_accel_x_raw
   - 或者用 i2cget 直接读寄存器
```

**验收标准：** 三个模块各有一条「能读到数据」的证据。

### 阶段 2：单模块能力（3-5 天）

```
1. 摄像头 + YOLO
   - 用 RKNN 部署 YOLOv8n（前项目已验证 62 FPS）
   - 实时检测 + 画框 + 保存截图

2. 语音唤醒 + 录音
   - 唤醒词触发 → 录音 3 秒 → 保存 wav
   - 验证唤醒率/误唤醒率

3. IMU + 姿态解算
   - 读原始数据 → 跑 Madgwick 滤波 → 输出 roll/pitch/yaw
   - 验证：静止时 roll/pitch 应接近 0
```

### 阶段 3：组合应用（5-10 天）

**选一个做深：**

**方案 A：语音视觉助手（推荐入门）**
```
唤醒 → 拍照 → YOLO 检测 → LLM 生成描述 → TTS
```

**方案 B：事件触发监控**
```
摄像头运动检测 + IMU 交叉验证 → 拍照 → LLM 描述 → 通知
```

**方案 C：姿态稳定视频**
```
IMU 数据 → 实时图像防抖 → 录制稳定视频
```

## 六、常见坑（提前预警）

| 坑 | 症状 | 解法 |
|---|---|---|
| **MIPI 排线接反** | 开机黑屏/不启动 | 排线金手指方向，板子丝印有 ▲ |
| **UART 冲突** | 板子不启动 | SU-03T 别接 ttyS2（那是 console）|
| **I2C 地址冲突** | i2cdetect 看到重复地址 | MPU9250 默认 0x68，可改 0x69 |
| **供电不足** | 反复重启 | 三件套 + 板子需要 5V/4A+ |
| **CSI 摄像头没时钟** | dmesg 有 csi error | 设备树要配 `clock-frequency` |
| **IMU 没上拉** | I2C 读不到 | 需要 4.7kΩ 上拉到 3.3V |
| **语音模块电平** | 烧 IO | SU-03T 是 3.3V，别接 5V |

## 七、一个战略判断

**加上这三个模块后，RK3588 的定位变了：**

| 之前 | 现在 |
|---|---|
| 「跑分板」—— 测 NPU 能跑多少 tok/s | 「具身终端」—— 能看、能听、能动 |

**这恰好补上了 4060 Ti 那边的短板：**
- 4060 Ti 有算力（59 tok/s），但**没有传感器**（是台主机）
- RK3588 算力弱（32 tok/s @0.5B），但**有完整的物理世界接口**

**⇒ 两台机器可以分工：**
```
RK3588（端侧感知）  →  摄像头/语音/IMU 采集 + 轻量推理
      ↓ 网络
4060 Ti（重算力）    →  复杂 VLM 推理 / 大模型
```
**这是「端-边-云」架构的本地版。**
