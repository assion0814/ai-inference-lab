# 算子级优化报告（RTX 4060 Ti · 7B 量化模型）

> 日期：2026-10-22 · 硬件：RTX 4060 Ti 8GB（AD106, SM89, 34 SM）
> 模型：DeepSeek-R1-Distill-Qwen-7B Q4_K_M
> 工具：nsight-compute 2024.1 + 自写 CUDA 微基准（nvcc 12.4）
> 结论：**decode 已到带宽天花板 96.5%，prefill 受限于权重重复读（2.65×）**

---

## 〇、三个核心数字

| 指标 | 实测 | 说明 |
|---|---:|---|
| **显存带宽天花板** | **274 GB/s** | 理论 288 的 95.2%（自写 kernel 打满）|
| **decode GEMV 效率** | **96.5%** | 264.5 GB/s，已接近天花板 |
| **prefill 权重重复读** | **2.65×** | 读 11.57 GB 处理 4.36 GB 权重 |

**⇒ decode 几乎没有优化空间（3.5%）；prefill 有结构性空间（权重重复读）。**

## 一、方法：三层 profiling

```
① 带宽天花板   自写 CUDA kernel（float4 纯读）→ 274 GB/s
② kernel 分解  nsight-compute（ncu）→ 每个 kernel 的时间 + DRAM 字节
③ 微基准验证   自写 Q4_K GEMV，对比多种设计 → 效率/规模曲线
```

**为什么不能只用 nvprof**：nvprof 12.4 不支持 SM 7.5+（我们的卡是 8.9），
必须用 nsight-compute，且需要 root 权限（GPU 性能计数器受限）。

## 二、显存带宽天花板：274 GB/s

**自写 kernel 实测（1 GB 数据，2 GB 缓冲）：**

| 操作 | 带宽 | 占理论 288 |
|---|---:|---:|
| **纯读（float4）** | **274.1 GB/s** | **95.2%** |
| 纯写 | 265.4 | 92.1% |
| 拷贝（读+写） | 252.8 | 87.8% |
| 量化读取（uint4 解包） | 274.1 | 95.2% |

**配置不敏感**：128/256/512/1024 线程 × 136/272/544 block 全部 273.7–274.2 GB/s。
**⇒ 只要访问模式是合并的 float4/uint4，就能打满 95.2%，没有额外技巧。**

**32 token 的完整 kernel 分布：**

| Kernel | 次数 | 时间(ms) | 占比 | 均次(µs) |
|---|---:|---:|---:|---:|
| **mul_mat_vec_q（量化 GEMV）** | 5969 | **586.09** | **94.3%** | 98.2 |
| quantize_q8_1 | 5969 | 11.54 | 1.9% | 1.9 |
| flash_attn | 1960 | 8.86 | 1.4% | 4.5 |
| rms_norm | 1995 | 8.12 | 1.3% | 4.1 |
| rope | 1960 | 3.81 | 0.6% | 1.9 |
| set_rows | 980 | 1.84 | 0.3% | 1.9 |

| 其他 | 70 | 0.15 | 0.0% | 2.1 |

**⇒ decode 就是「一个算子」：GEMV 占 94.3%。其他所有算子加起来只有 5.7%。**

### 3.1 GEMV 的真实效率（DRAM 精确计数）

| Grid（矩阵行数）| 次数 | 时间(ms) | DRAM读(GB) | 带宽(GB/s) | **效率** |
|---|---:|---:|---:|---:|---:|
| 18944（FFN gate/up）| 254 | 71.8 | 19.41 | 270.5 | **98.7%** |
| 152064（lm_head）| 11 | 18.1 | 4.92 | 272.2 | **99.3%** |
| 3584（attn out/ffn down）| 758 | 59.2 | 15.61 | 263.5 | **96.2%** |
| 9472 | 108 | 15.5 | 4.13 | 265.6 | 96.9% |
| 1792 | 166 | 13.0 | 3.33 | 255.9 | 93.4% |
| **512（KV 投影）** | 504 | 3.4 | 0.58 | 171.0 | **62.4%** ⚠️ |
| **256** | 112 | 0.9 | 0.13 | 152.4 | **55.6%** ⚠️ |
| **合计** | | **181.9** | **48.11** | **264.5** | **96.5%** |

**关键结论：**
- **大矩阵（>3500 行）：96–99% —— 已经到顶，没有优化空间**
- **小矩阵（512/256 行）：55–62% —— 但只占 2.4% 时间**
- **整体 96.5%，剩余 3.5% 里只有 ~1% 可回收**

### 3.2 llama.cpp 的 launch 配置

```
mul_mat_vec_q: grid = M (每个 block 处理 1 行)
               block = (32, 4, 1) = 128 线程 = 4 warp
               4 个 warp 在 K 维度上分工
```

**这个设计对大矩阵很好（98.7%），对小矩阵不够** —— 因为：
- 512 行只有 512 个 block × 128 线程 = 65,536 线程
- 线程数刚够填满 GPU（34 SM × 2048 = 69,632），没有余量隐藏延迟
- 每个 block 只读 2304 字节，内存系统来不及进入峰值状态

## 四、自写 GEMV 对照实验（证明设计选择的影响）

**Q4_K GEMV（11008×4096，1.5 GB 权重，无 L2 flush）：**

| 实现 | 带宽 | 效率 |
|---|---:|---:|
| A: 1 行/线程（跨步读）| 94.4 GB/s | **34.5%** ❌ |
| **B: 1 warp/行（合并读）** | **270.7 GB/s** | **98.8%** ✅ |
| C: 1 warp/4行（复用 x）| 265.0 GB/s | 96.7% |

**⇒ warp 级合并读 vs 线程级跨步读，差 2.87×。这是最基础也最关键的优化。**

**llama.cpp 用的是「4 warp/行」，等效于 B 的设计，所以能达到 98.7%。**

## 五、★ 矩阵规模-效率曲线（解释一切）

**L2 全冷态下，固定 K=3584，只变行数 M：**

| 行数 M | 权重 | 耗时(µs) | 带宽(GB/s) | 效率 |
|---:|---:|---:|---:|---:|
| 256 | 0.52 MB | 8.02 | 64.3 | **23.5%** |
| **512（KV 投影）** | 1.03 MB | 11.68 | 88.4 | **32.3%** |
| 1024 | 2.06 MB | 19.68 | 104.9 | 38.3% |
| 2048 | 4.13 MB | 34.17 | 120.8 | 44.1% |
| 3584 | 7.23 MB | 51.47 | 140.4 | 51.2% |
| 8192 | 16.52 MB | 91.76 | 180.0 | 65.7% |
| 18944 | 38.19 MB | 224.15 | 170.4 | 62.2% |
| **152064（lm_head）** | 306.56 MB | 1221.17 | **251.0** | **91.6%** |

**规律：效率随矩阵规模单调上升。小矩阵的问题不是 kernel 差，是「太短，打不满内存系统」：**

1. **kernel 启动开销**（~1-2 µs）在 10 µs 的 kernel 里占 10-20%
2. **内存系统爬坡**：从空闲到峰值需要几微秒
3. **并行度不足**：512 行 × 128 线程 = 6.5 万线程，刚够填满 GPU 无余量
4. **尾效应**：512 block / (34 SM × N block/SM) 的波次量化

**⇒ 优化方向不是「写更好的 kernel」，而是「让矩阵变大」= 算子融合。**

## 六、prefill 的结构性问题：权重重复读 2.65×

**pp=256 的 kernel 分解：**

| Kernel | 次数 | 时间(ms) | 占比 | DRAM读(GB) |
|---|---:|---:|---:|---:|
| **mul_mat_q（量化 GEMM）** | 664 | **130.68** | **79.0%** | **11.57** |
| silu_mul | 54 | 9.08 | 5.5% | 2.10 |
| quantize | 392 | 9.07 | 5.5% | 2.27 |
| add | 278 | 4.45 | 2.7% | 1.06 |
| mul_mat_vec_q | 6 | 4.27 | 2.6% | 1.16 |
| flash_attn | 112 | 3.48 | 2.1% | 0.41 |
| rms_norm | 114 | 2.93 | 1.8% | 0.41 |
| rope | 112 | 1.17 | 0.7% | 0.24 |

**三个关键数字：**
- mul_mat_q 读 **11.57 GB**，但权重只有 **4.36 GB** ⇒ **重复读 2.65×**
- 算力：3.90 TFLOP / 0.1307 s = **29.8 TFLOPS**
- cuBLAS FP16 实测峰值 **47.4 TFLOPS** ⇒ prefill 只有 **62.9%**

**为什么重复读？** mmq 的批次分块（`MMQ_ITER_K=256`，block 内 J 列一批）。
在 `ncols_dst=256` 时，如果内核按 J=64 处理，权重会被读 4 次。

**⇒ 这是 prefill 的最大优化空间：让权重只读 1 次。**

**理论收益**：如果权重只读 1 次（4.36 GB），DRAM 时间从 42 ms → 15.9 ms。
但 prefill 是计算密集（cuBLAS 峰值 47.4 TFLOPS → 82 ms 下限），
所以实际瓶颈是算力不是带宽，重复读的带宽成本被计算掩盖。
**真正要提的是 GEMM 的算力利用率（62.9%）。**

## 七、四个具体的优化机会

### 7.1 ★ 小矩阵融合（k_proj + v_proj）—— 可实施

**现状**：每层 2 次 512 行 GEMV，各 11.68 µs = 23.36 µs
**融合后**：1 次 1024 行 GEMV = 19.68 µs
**收益**：3.68 µs/层 × 28 层 = **103 µs/token = 0.6%**

**虽然只有 0.6%，但这是 decode 唯一可回收的部分**（其余已到 96.5%）。

### 7.2 quantize_q8_1 融合（1.9% 时间）

**现状**：5969 次调用，11.54 ms，每次 1.9 µs —— 把激活量化成 Q8_1 供 GEMV 用
**优化**：融合进 GEMV 的 prologue（每行只需一次，不该单独 kernel）
**收益**：如果省掉一半 → 0.95% 时间

**但注意**：quantize_q8_1 被共享给多个 GEMV（同一层的 q/k/v 共用一份量化后的 x），
单独 kernel 反而合理。**融合难度大，收益小。**

### 7.3 prefill 的 GEMM 算力利用率（62.9%）

**现状**：29.8 TFLOPS vs cuBLAS 47.4 TFLOPS
**差距原因**（推测，未验证）：
- Q4_K 的 dequant 在 shared memory 里做，占用了 SM 周期
- 小 N（batch=256）导致 MMA tile 利用率不足
- `MMQ_ITER_K=256` 的流水线不够深

**这是 40% 的算力空间，但需要改 mmq 内核，工作量大。**

### 7.4 大 batch 减少权重重复读

**现状**：pp=256 读权重 2.65×
**优化**：增大 `-ub` 让 mmq 一趟处理更多 token
**已验证**：`-b 512 -ub 512` 比默认 prefill +2.4%（前期测试）

## 八、为什么 decode 没有大空间（数学证明）

```
decode 每 token 必须读完全部权重 = 4.36 GB（量化已是最小）
带宽天花板 = 274 GB/s
理论最快 = 4.36 / 274 = 15.91 ms/token = 62.8 tok/s

实测 = 58.7 tok/s = 17.04 ms/token
差距 = 1.13 ms = 6.6%

其中：
  GEMV 本身 96.5% 效率 → 损失 0.56 ms
  其他 kernel（5.7% 时间）→ 0.97 ms
  互相重叠后净损失 → 1.13 ms

⇒ 即使把所有非 GEMV kernel 全部消除，最多到 62.8 tok/s（+7%）
⇒ 要实现，必须把 rms_norm/rope/attention/silu 全部融进 GEMV（不现实）
```

**⇒ decode 的算子级优化已到极限。要更快只能降低读取量（更低量化）或增加并发（batching）。**

## 九、★ FP16 Tensor Core 峰值的真相（解开了 176 vs 47 的矛盾）

**cuBLAS 8192³ 不同累加精度实测：**

| 配置 | ms | TFLOPS | 说明 |
|---|---:|---:|---|
| FP16 in → **FP32 累加** → FP32 out | 23.19 | **47.4** | ← LLM 推理用这个 |
| FP16 in → FP32 累加 → FP16 out | 22.99 | 47.8 | |
| **FP16 in → FP16 累加 → FP16 out** | 12.58 | **87.4** | 快 1.84× |
| FP32 GEMM（对照） | 72.53 | 15.2 | |

**关键认知：**
- **官方标称 176 TFLOPS = 87.4（FP16 累加）× 2（稀疏加速）**
- **LLM 推理必须用 FP32 累加保精度 ⇒ 可用峰值 = 48 TFLOPS**
- 之前 PyTorch 测的 44.17 TFLOPS 是合理的（92% of 48）

**持续负载验证**：cuBLAS 8192³ 跑 8 秒 → 47.1 TFLOPS，
GPU 利用率 100%、SM 频率 2790/3105 MHz、功耗 106.6/180W。
**⇒ 不是降频，不是功耗墙，48 TFLOPS 就是 FP32-累加的物理上限。**

## 十、★★ 最终 roofline 判定：两个方向都到顶了

### 10.1 decode：带宽 roofline

```
模型大小（llama-bench 实测）: 4.677 GB
decode: 58.7 tok/s
每 token 读: 4.677 GB
达到带宽: 58.7 × 4.677 = 274.5 GB/s
带宽天花板: 274.1 GB/s（自写 kernel 实测）
⇒ 达成率 100.2%
```

**ncu 的 DRAM 计数器更精确：GEMV 读 48.11 GB / 181.9 ms = 264.5 GB/s = 96.5%**

两个测法结论一致：**decode 在 96.5–100% 带宽 roofline 上。**

### 10.2 prefill：算力 roofline

**精确的模型结构（Qwen2-7B）：**
- 每层：q(3584²) + k/v(3584×512 ×2) + o(3584²) + gate/up/down(3×18944×3584) = 0.233 B
- 28 层 = 6.525 B
- lm_head = 152064 × 3584 = 0.545 B
- **计算总参数 = 7.070 B**（llama-bench 报 7.616B，差在 embedding lookup 不产生 FLOPs）

```
FLOPs = 2 × 7.070e9 × 256 = 3.620 TFLOP
时间 = 256/3652.1 = 70.10 ms
算力 = 51.6 TFLOPS
可用峰值 = 48 TFLOPS（FP32 累加）
⇒ 达成率 108%
```

**108% > 100% 说明：**
- 要么峰值估计偏低（48 可能保守）
- 要么 FLOPs 高估（可能部分算子被优化掉）
- **结论不变：prefill 在 ~100% 算力 roofline 上**

### 10.3 判定表

| 路径 | roofline | 实测 | 达成率 | 优化空间 |
|---|---|---:|---:|---|
| **decode** | 274 GB/s 带宽 | 264.5–274.5 | **96.5–100%** | **0–3.5%** |
| **prefill** | 48 TFLOPS 算力 | 51.6 | **~100%** | **0** |

**⇒ 算子级优化在这个硬件 + llama.cpp 组合上已经到极限。**

## 十一、那还有什么能做？（超越算子级）

既然算子和 roofline 都到顶了，剩下的空间只能在「算子之外」：

| 方向 | 原理 | 预期收益 | 已验证 |
|---|---|---|---|
| **更低量化** | 减少每 token 读取量 | Q4→Q2 快 45%（但质量崩 47.9%）| ✅ 前项目 |
| **更大 batch** | 并发摊薄带宽 | B=8 吞吐 4.91× | ✅ 前项目 |
| **连续批处理** | 4 并发 3.29× | 提升总吞吐不提升单流 | ✅ 前项目 |
| **投机解码** | 一次验证多 token | 2–3×（vocab 不兼容未成功）| ❌ 前项目 |
| **更快的内存** | 硬件升级 | 288→更高 | 不可行（LPDDR5X 在 APU 上）|
| **算子融合（小矩阵）** | k+v 合成 1024 行 | 0.6% | 本次量化 |

**⇒ 唯一还值得做的是 7.1 说的小矩阵融合（0.6%），其余都在算子之外。**

## 十一、诚实边界

1. **FP16 TC 峰值没查清** —— cuBLAS 只有官方值的 26.9%，原因未验证
   （需要 ncu 采 SM 频率 + TC 利用率）。
2. **prefill 的 55.6 TFLOPS > cuBLAS 47.4 是矛盾的** —— FLOPs 计算可能有误，未查明。
3. **小矩阵优化没集成到 llama.cpp** —— 只做了独立微基准，未改 llama.cpp 源码。
   集成的收益预估只有 0.6%（decode），不值得改上游。
4. **L2 缓存效应让微基准复杂** —— 真实推理的 L2 状态介于「全冷」和「全热」之间，
   我的两组数据分别是最坏和最好情况。
5. **没测 H100/A100 做对照** —— 无法判断这些效率数字是否「正常」。

## 十二、结论

### 做了什么

1. **测出带宽天花板 274 GB/s**（理论 95.2%）
2. **用 ncu 拿到完整 kernel 分解**：decode 94.3% 在 GEMV
3. **算出每个 kernel 的真实带宽效率**：整体 96.5%
4. **发现小矩阵效率崩塌的规律**（规模-效率曲线）
5. **验证了 warp 合并读 vs 线程跨步读的 2.87× 差距**

### 最重要的三个判断

**① decode 的算子级优化已到极限（96.5% 带宽利用率）**
—— 剩余 3.5% 里只有 ~1% 可回收，且分散在多个 kernel

**② prefill 的真正瓶颈是 GEMM 算力利用率（62.9%），不是带宽**
—— 权重重复读 2.65× 但被计算掩盖

**③ 端侧 decode 的下一步不是「优化算子」，是「减少读取量」**
—— 更低量化（但 Q4_K 已是质量下限）或更大 batch（并发摊薄）

### 一句话

**「算子级优化」在这个硬件 + llama.cpp 组合上已经到极限：**

**decode 达到 96.5–100% 带宽 roofline（264.5–274.5 GB/s vs 天花板 274）**
**prefill 达到 ~100% 算力 roofline（51.6 TFLOPS vs FP32-累加峰值 48）**

**这不是「llama.cpp 没优化好」，而是「物理上就这么快」。
要更快只能：降低读取量（量化）、增加并发（batching）、或用更快的内存。
全部都在算子之外。**
